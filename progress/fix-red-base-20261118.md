# fix-red-base-20261118: flaky `test (22)` on main (2026-11-18)

- Failing checks on main HEAD `0b95c26`: `verify / test (22)` (run 44386236167) and `host-stripe-mode / mode` (run 44371593916).
- `test (22)`: `test/wrap-otlp.test.js` "#239 AC4: collector hang never affects the run" failed with `lag 6314`. A hung collector makes the final OTLP flush wait its full 5 s cap (`FINAL_FLUSH_MS`), which is correct. The e2e test allowed only 1 s on top of that for child exit, server close, summary write and process exit, and a loaded self-hosted runner took 1.3 s. The same commit passed on a rerun (run 44371585023). No product bug.
- Fix: the e2e bound is now `POST_TIMEOUT_MS - 1000` (9 s), imported from `src/otlp.js`. This still fails if the cap is missing, since a hung collector would then cost the full 10 s POST timeout or never end. The hang case also asserts lag >= `FINAL_FLUSH_MS`, which proves the run really waited for the deadline. The exact deadline stays covered deterministically in `test/otlp-export.test.js`.
- `mode` (not fixed, owner-blocked): someone dispatched `host-stripe-mode` with `MODE=live` by hand, against a deploy host whose ED25519 key is not in the pinned `infra/ssh/costcap-deploy.known_hosts`. It failed closed at `StrictHostKeyChecking`, by design. Agents may not re-pin the host key or flip Stripe to live. Rajvir has to verify the host key out of band and choose the mode (see `progress/fix-red-base-20261114.md`). It is a manual workflow_dispatch run, so a later push does not re-trigger it.
- A second manual `MODE=live` dispatch (run 44395246393, 20:50Z) got past the host key check but failed with `Permission denied (publickey)`: the host does not accept the `COSTCAP_DEPLOY_SSH_KEY` secret. Only the owner can fix that (the secret or the host's authorized_keys); no agent change.
